# 项目术语表（招租小程序系统）

本文件记录系统里各个角色和核心概念的准确定义，方便后续讨论、写PRD的时候，"用户"这种词不会一会儿指这个人、一会儿指那个人。

## 角色

### 看房人
打开小程序、浏览房源、发起微信咨询的人。**不需要做任何"注册/登录"的操作**，但系统会借助微信本身提供的身份标识（openid），悄悄识别出"这是同一个人"，本人完全感觉不到这件事在发生。

### 租户
已经签了合同的人。**租户不是一个全新注册的账号，而是"看房人"这个身份往前走了一步**：一旦看房人签约，系统会自动把他之前留下的看房、咨询记录关联到租户身份上，不需要本人重新填一遍资料。租户以后再打开小程序，同样是免密识别身份，能看到属于自己的合同信息。

租户有四种状态。状态不是只看"最新一份合同"，而是把这个人名下**所有合同**放在一起判断：
- **在租**：只要名下还有一份"生效中"的合同，就显示在租。即使这份合同已经过了到期日，但管理员还没有确认结束，也仍然按在租处理。
- **待入住**：没有"生效中"的合同，但还有一份或多份"待生效"的合同，已经签了但还没开始住。
- **曾租过**：没有"生效中"或"待生效"的合同，并且历史上至少有一份合同标记为"到期结束"或"提前退租"，说明这个人确实住过。
- **签约未入住**：没有其他更高优先级的状态，历史合同全部是"签约未入住取消"，说明这个人签过合同但从未真正入住。

判断顺序固定为：先看有没有"生效中"，再看有没有"待生效"，再看有没有真实住过的历史，最后才判断是否只是"签约未入住"。因此，任何一份正在执行的合同，都会优先于更早或更晚的历史记录。

"曾租过"和"签约未入住"要严格分开，因为前者是真的住过，后者只是留了一条差点租成的痕迹，运营上完全是两件事。
_Avoid_: 用"曾租过"笼统覆盖"签约未入住"的情况；把"待入住"和"在租"混为一谈。

### 管理员
负责维护房源、租户、合同这些数据的人，也就是房东本人（以后可能有帮手一起管）。**管理员是单独一套账号体系，需要正式登录**（不是微信免密识别），因为管理员的操作会真正改动数据，需要更明确的身份确认。初期不区分管理员之间的权限，谁登录进来能做的事都一样，但账号本身是可以有多个的。

## 核心概念

### 房源
一套要出租的房子，有三种状态：
- **可以租**：没有任何生效中或待生效的合同，看房人能在列表里看到。
- **已预定**：已经和某个人签了合同，但合同还没到起租日期，人还没搬进来。看房人看不到这套房，但它跟"已租出"在运营意义上不是一回事——这里其实是空的，只是名义上被占了。
- **已租出**：合同已经生效，租户已经在住。

这三态之间的转换由房源名下所有合同共同决定：有"生效中"就显示"已租出"，没有生效中但有"待生效"就显示"已预定"，两者都没有才显示"可以租"。已结束和已取消的合同只保留历史，不影响当前状态。管理员不直接切换房源状态。
_Avoid_: 把"已预定"和"已租出"混用同一个标签，两者对应的合同阶段不同，运营上需要能一眼区分。

### 合同
租户和房东就一套房源达成的租赁约定。合同有自己的状态机：
- **待生效**：已经签了，但还没到起租日期。对应房源状态"已预定"，对应租户状态"待入住"。
- **生效中**：已经到了起租日期，或已经开始入住但管理员还没有确认结束。对应房源状态"已租出"，对应租户状态"在租"。系统会按起租日期检查待生效合同是否可以开始，但必须先确认同一房源没有其他仍未结束的生效中合同。
- **已结束**：合同走完了它的生命周期，结束时必须选择一个**终止原因**：
  - **到期结束**：租期正常走完。只有这个租户没有其他生效中或待生效合同，才会显示"曾租过"。
  - **提前退租**：租期内提前解约，租户曾经真实入住过。只有这个租户没有其他生效中或待生效合同，才会显示"曾租过"。
  - **签约未入住取消**：还没到起租日期（也就是合同还在"待生效"阶段）就取消了合同，租户从未真正入住；只有这个租户没有其他合同经历，才会显示"签约未入住"。

合同结束时还要记录**实际结束日期**。正常到期时通常就是原来的到期日；提前退租时填写真正退租的日期；签约未入住取消不算真实入住。这个日期用来说明房子实际被占用到哪一天，也用来检查后面的合同是否冲突。

合同建立、合同开始生效、管理员确认结束这几个动作，会让系统重新查看全部相关合同，再更新房源和租户的显示状态。合同到了到期日期不会自动变成"已结束"；管理员确认租期确实结束后，才需要手动标记结束并选择原因。
_Avoid_: 把合同状态简化成"进行中/已结束"两态，这会丢失"签了但还没入住"和"结束原因是什么"这两类真实存在的信息。

### 续租
租户在原合同到期前后，就同一套房源和房东再签一份新的租赁约定。**续租不是修改原合同的到期日期，而是先新建一份合同**，新合同上记录"续租自哪一份旧合同"。旧合同不会在创建续租合同时提前结束，到了约定到期日后，仍需管理员确认实际结束，再把旧合同标记为"已结束"。这样每一段租期的真实条款（租金、押付方式）都会被完整保留下来，也不会因为提前操作续租而伪造旧合同的结束时间。

同一套房源的合同租期不能重叠。新合同保存前，系统必须检查这套房源已有的、没有被取消的合同；未结束合同按约定到期日检查，已经提前结束的合同按实际结束日期检查，只要日期有重叠就不允许保存，并明确告诉管理员是哪一份合同冲突。续租通常从旧合同到期日的次日开始，因此可以提前建立，但不能覆盖旧合同的租期。如果旧合同实际结束得更晚，管理员必须先调整新合同日期，不能让两份合同在同一天占用同一套房源。

### 咨询记录
一个看房人对**某一套具体房源**发起接触之后，围绕这次接触留下的跟进痕迹。核心规则：
- **一人一房一条**：同一个看房人只对同一套房源保留一条咨询记录；这个人再来问同一套房源，是在这条记录里追加一条跟进备注，不新建记录。如果这个人问的是另一套房源，才会新建另一条记录。
- **系统自动创建**：看房人在房源详情页点击"咨询"按钮跳转到微信客服会话的那一刻，系统自动生成这条记录（谁、问的哪套房、什么时候）。管理员不需要手动新建，只需要在聊完之后手动追加"聊得怎么样"这类系统看不到的内容。
- **有自己的状态**：跟进中 / 未成交 / 已转合同。签约那一刻，对应的咨询记录自动标记为"已转合同"；管理员判断这个人确定没戏了，可以手动标记"未成交"。

咨询记录是"看房人"和"房源"之间的关系对象，不是挂在房源身上的一段文本备注，也不是挂在看房人身上的一份笼统档案。
_Avoid_: 把跟进内容当成房源的一个备注字段；把同一个人对不同房源的咨询混在一条记录里。

## 已确定的关键决策

- **系统模块范围**：招租 + 咨询/跟进 + 租户 + 合同，这四块是这次设计的主体。收款/报修/多房东多项目这些暂时不在本次设计范围内，但在概念上先留出扩展的口子，不现在就设计细节。
- **身份识别方式**：看房阶段不需要用户主动登录，靠微信的身份标识悄悄识别；管理端需要正式的账号密码登录。这样既保证普通用户零门槛看房，又保证后台数据能追踪到同一个人的完整轨迹。
- **看房人与租户的关系**：是同一个人身份的不同阶段，数据要关联打通，不是两套互不相关的东西。
- **管理端账号数量**：预留多账号的能力（房东本人之外，以后可能有帮手），但初期不做权限区分。
- **看房人 → 咨询记录 → 租户的中间链路**：看房人对某套房源的每一次接触，都落在一条独立的"咨询记录"上，而不是混进房源的备注里；这条记录后续要么被标记"未成交"，要么在签约时自动转成"已转合同"，衔接到租户身份。
- **房源三态**：可以租 / 已预定 / 已租出，替代原来简单的"可以租/已租出"二态，用来区分"签了但还没入住"和"已经在住"这两种运营意义不同的情况。
- **合同三态**：待生效 / 生效中 / 已结束。系统会按起租日期检查待生效合同是否可以开始，但不会因为到期日到了就自动结束合同；到期合同需要管理员确认后手动结束。
- **合同结束要选终止原因**：到期结束 / 提前退租 / 签约未入住取消，三选一，方便以后统计退租率、毁约率，不用靠人工翻备注。
- **续租是新建关联合同，不是改日期**：旧合同不提前结束，等实际到期并由管理员确认后再结束，保留每一段租期的真实条款历史。
- **同一房源的合同日期不能重叠**：保存新合同时检查整套房源的合同日期，冲突就不能保存；到期日按日历日期处理，下一份无缝续租合同从次日开始。
- **到期日不等于自动结束**：到期日到了只显示"已到期，待确认结束"提醒，合同仍保留原状态，直到管理员确认并填写结束原因。
- **合同取消（签约未入住）不抹掉痕迹**：人和合同记录继续保留。房源和租户状态都按其他合同重新计算；只有房源没有其他生效中或待生效合同，才恢复"可以租"，只有这个人没有其他合同经历，才显示"签约未入住"。
