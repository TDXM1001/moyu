# 招租系统 PRD（招租 + 咨询/跟进 + 租户 + 合同）

## 1. 文档说明

这份文档是给AI设计UI图用的产品需求说明。内容按照"这个系统是干什么的、给谁用的、事情是怎么一步步走完的、每个页面上要放什么"这个顺序写，方便直接看懂再画图，不需要再补充背景。

这份文档里用到的"看房人""租户""管理员""咨询记录"这几个词，都有明确的定义，写在同目录下的 `CONTEXT.md` 里，如果有疑问可以对照那份文件核对。

文档里有些地方标了"待定"，意思是这块还没最终拍板，暂时不影响页面设计，等真正要开发的时候再定。

---

## 2. 系统是做什么的

这不是一个只管"发房源"的小工具，而是一整套围绕"一套房子从空置到租出去、再到租期结束"这件事转起来的系统，目前包含四个互相关联的部分：

- **招租**：把要出租的房子展示出来，让想租的人能看到、能联系上。
- **咨询/跟进**：记录每一个看房人对每一套房源的接触和后续跟进进展，是招租和签约之间不能少的中间环节。
- **租户**：记录已经签约的人的信息，跟他们之前的看房、咨询记录关联起来。
- **合同**：记录一套房子和一个人之间的租赁约定，是连接"房源"和"租户"这两块的关键纽带。

这四块不是各自独立的功能，而是一件事的四个阶段：房子先要被人看到（招租），有人看中了要联系并跟进（咨询），谈成了要签约（合同），签约的人要被系统记住（租户）。以后如果要加收款、报修这些功能，都是挂在这四块已经搭好的骨架上继续扩展，不需要推倒重来。

## 3. 角色说明

（详细定义见 `CONTEXT.md`，这里简单复述一下方便对照页面设计）

- **看房人**：打开小程序看房源、发起咨询的人，不需要登录，系统会借助微信自带的身份标识悄悄认出"这是同一个人"，本人无感。
- **租户**：已经签约的人。本质上是"看房人"这个身份往前走了一步，签约那一刻，系统会自动把这个人对应这套房源的咨询记录接到他的租户身份上。
- **管理员**：也就是你（以后可能有帮手），负责维护房源、咨询记录、租户、合同这些数据，需要正式登录，账号可以有多个，暂时不区分权限。

## 4. 核心业务流程（一套完整的闭环）

这是整个系统最核心的一条线，所有页面都是为了让这条线走得顺：

1. **房子空出来** → 管理员把房源信息录入系统，状态设为"可以租"。
2. **看房人打开小程序** → 在房源列表里翻看（这个阶段系统已经在悄悄记录"这个人看了哪些房"，只是他自己感觉不到）。
3. **看中了某套房子** → 点进详情页，点"咨询"按钮，跳转到微信客服会话联系管理员。**这一步系统会自动生成一条"咨询记录"**，挂在"这个人 + 这套房源"这一对关系上，不需要管理员手动新建。
4. **双方在微信上聊** → 约时间看房。管理员可以随时回到这条咨询记录里，补充跟进备注（比如"觉得贵""下周三看房"）。如果同一个人后续又来问同一套房，追加在同一条记录里，不会拆成两条。
5. **看房之后，两种结果**：
   - **谈成了** → 管理员在系统里为这个人和这套房源**建立一份合同**，合同初始状态是"待生效"。这个动作一旦完成，会自动触发三件事：
     a. 这套房源的状态**自动**从"可以租"改成"已预定"（还没到起租日期，人还没搬进来）。
     b. 这个"看房人"**自动升级**为"租户"，状态是"待入住"，对应这套房源的咨询记录自动标记为"已转合同"。
     c. 这个人之前对这套房源的咨询、跟进记录被接到他的租户身份上。
   - **没谈成** → 房子继续挂在"可以租"状态，管理员在这条咨询记录里标记"未成交"，方便后续判断要不要调整信息或价格，也方便主动盘点"最近有哪些人在看房但一直没结果"。
6. **到了起租日期** → 系统检查这份"待生效"合同是否可以开始。如果同一房源没有其他仍未结束的"生效中"合同，就把它改成"生效中"；如果有，就暂不改动，并提醒管理员先处理冲突的旧合同。合同开始后，房源显示"已租出"，租户状态按他名下所有合同重新计算。
7. **合同到期或者提前退租** → 到期日到了不会自动结束合同。系统只提醒管理员"这份合同已经到期，请确认是否结束"；管理员确认后，在合同上标记"已结束"，选择终止原因（到期结束 / 提前退租），并填写实际结束日期。系统检查实际结束日期是否与后面的合同冲突，确认无冲突后，再根据这套房源和这个租户的全部合同重新计算状态。如果后面已有一份起租日已经到达的待生效合同，旧合同结束后系统立即再次检查它是否可以开始。
8. **如果是续租** → 管理员从旧合同详情页点"续租"，系统自动带出同一套房源、同一个租户，建议把新合同起租日填为旧合同到期日的次日。管理员填写新的租期和租金后，系统先检查同一房源的合同日期是否重叠；有重叠就不允许保存。保存后只新建一份"待生效"的新合同，记录它续租自哪一份旧合同，旧合同继续保持原状态，不能因为提前创建续租合同就被提前结束。
9. **如果签约后还没到起租日期就不租了** → 管理员取消这份"待生效"合同，终止原因选"签约未入住取消"。系统保留合同和人的记录，再查看这套房源及这个人名下的其他合同：房源没有其他生效中或待生效合同才恢复"可以租"；这个人没有其他合同经历才显示"签约未入住"。如果取消的是续租产生的新合同，旧合同仍在生效中，房源继续显示"已租出"，租户继续显示"在租"。
10. **房子又空出来** → 只有当这套房源已经没有任何"生效中"或"待生效"合同，系统才显示"可以租"，再回到第1步重新走一遍。

**这里最关键的几处联动**，是这次调整里新加的核心设计：
- 点击咨询按钮 → 自动生成咨询记录（人 + 房源，一对一，重复咨询追加不新建）。
- 建立合同 → 房源自动变"已预定" + 看房人自动升级为"待入住"租户 + 对应咨询记录自动标记"已转合同"。
- 到起租日期 → 系统检查没有未结束的生效中合同后，才把待生效合同改为"生效中"；房源和租户状态都按全部合同重新计算。
- 合同到期 → 只产生"已到期，待确认结束"提醒，不自动结束；管理员确认结束并选择原因后，系统按全部合同重新计算状态。
- 合同正常结束 → 只有没有其他生效中或待生效合同的房源才恢复"可以租"；租户没有其他进行中的合同且历史上真实住过时，才显示"曾租过"。
- 合同签约未入住就取消 → 系统按房源其他合同情况决定是否恢复"可以租"，租户按全部合同历史判断，不会覆盖其他更重要的状态。
- 续租 → 新建关联合同，旧合同保持原状态直到实际结束，不是直接改日期，保留每一段租期的真实条款历史。
- 同一房源合同租期不能重叠；系统保存合同前检查冲突，发现冲突就阻止保存。

房源和租户的显示状态都由系统根据全部合同重新计算，管理员不需要分别改几处。只有"确认合同真正结束"这件事由管理员操作，因为系统不能替管理员判断租户是否真的搬走；到期日只能作为提醒，不能代替这个确认动作。

## 5. 页面清单（给UI设计用）

系统分两部分：**看房人能看到的部分**（只有招租相关的两个页面），和**只有管理员能看到的管理部分**（房源、咨询/跟进、租户、合同四块的管理页面）。

### 5.1 看房人侧页面

#### 页面A：房源列表页（首页）
- 打开小程序看到的第一个页面。
- 只显示状态为"可以租"的房源，已预定和已租出的都不会出现在这里。
- 每一条房源用卡片形式展示，卡片上放最重要的几个信息：图片、小区/位置、户型、面积、租金。
- 点击卡片，跳转到"房源详情页"。

#### 页面B：房源详情页
- 展示一套房子的完整信息，信息分两层：
  - **一眼就要看到的**：图片/视频、租金、小区/位置、户型、面积。
  - **往下翻能看到的**：朝向、楼层、押付方式、房源简介、联系方式说明。
- 页面底部放明显的"咨询/联系房东"按钮，点击跳转到微信客服会话（这一步会在后台自动生成一条咨询记录，看房人本人无感）。

### 5.2 管理员侧页面

管理员登录后，能看到一个总的管理入口，下面分四块：房源管理、咨询/跟进管理、租户管理、合同管理。这四块通过"人 + 房源 + 合同"这条线串起来，不是孤立的四个页面。

#### 页面C：房源管理列表
- 显示管理员名下**所有**房源，不管状态如何。
- 每条房源清楚标出当前状态：**可以租 / 已预定 / 已租出**（用三种不同颜色的标签区分）。
- 点击某条房源，如果它当前是"已预定"或"已租出"状态，页面上要能直接跳转看到关联的那份合同，不需要跑到合同模块里再去翻找；也能看到这套房源历史上收到过哪些咨询。
- 有"编辑"入口（进入页面D）和"新增房源"按钮。

#### 页面D：房源编辑/新增表单
- 填写或修改一套房子的详细信息，字段见第6节。
- 表单里有一个**状态显示**的地方（可以租 / 已预定 / 已租出）。这个状态由房源名下全部合同共同决定，管理员不能直接切换。若有合同日期冲突或到期未结束，页面要显示明确提醒和对应合同入口。
- 表单不再放"跟进备注"这个字段——每次咨询和跟进的记录，改到页面G（咨询/跟进列表）里按房源、按人查看，不再混进房源本身的信息里。

#### 页面E：租户管理列表
- 显示所有出现过的"租户"，状态分四种：**待入住 / 在租 / 曾租过 / 签约未入住**，用不同颜色的标签区分。
- 每条租户信息里能看到：这个人当前（或曾经）租的是哪套房、对应哪份合同、当前状态。
- 点击某个租户，能看到他的完整轨迹：签约前对这套房源问过什么（关联的咨询记录）、后来签了哪份合同、如果续租过还能看到完整的历史合同链——这是"看房人自动升级为租户、记录自动关联"这条设计规则在页面上的体现。

#### 页面F：合同管理列表
- 显示所有合同，标出状态：**待生效 / 生效中 / 已结束**，用不同颜色的标签区分；已结束的合同还要显示终止原因（到期结束 / 提前退租 / 签约未入住取消）。
- 点击某条合同，能看到详情：关联哪套房源、关联哪个租户、租期、租金等条款；如果是续租产生的合同，能看到它续租自哪一份旧合同，反过来旧合同上也能看到"已续租为新合同"的链接。
- 有"新建合同"入口：选择一套当前没有冲突合同的房源，选择或新建一个租户信息，填写租期和租金。保存前必须检查同一房源已有合同的租期，日期重叠就不允许保存；保存后房源和租户状态按全部合同重新计算。
- 每份"生效中"的合同上要有"标记结束"的操作。到期合同同样需要管理员确认后才能结束；操作时要求选择终止原因（到期结束 / 提前退租），之后系统按全部合同重新计算房源和租户状态。
- 每份"待生效"的合同上要有"取消"操作（对应终止原因"签约未入住取消"）。取消后保留记录，并按房源和租户的全部合同重新计算状态，不能无条件恢复"可以租"或改成"签约未入住"。
- 每份"生效中"或已到期临近的合同上要有"续租"按钮：点击后自动带出同一套房源、同一个租户，建议把新合同起租日填为旧合同到期日次日。保存前检查同一房源是否有日期重叠；保存后只新建一份关联的"待生效"合同，旧合同保持原状态，不能提前结束。旧合同到期后仍需管理员确认结束；若旧合同未结束，新合同到了起租日也不能自动变为"生效中"。

#### 页面G：咨询/跟进列表（新增）
- 集中展示所有"看房人对某套房源"的咨询记录，不用分别跑到房源详情或租户详情里才能看到。
- 每条记录显示：谁（看房人标识）、问的哪套房源、最近一次跟进时间、当前状态（**跟进中 / 未成交 / 已转合同**），状态用不同颜色的标签区分。
- 可以按状态筛选，方便管理员主动盘点"最近有哪些人在看，但还没结果"，避免这些人沉底被遗忘。
- 点击某条记录，能看到完整的跟进备注历史（每次追加的备注按时间排列），并能在这里补充新的跟进备注，或手动标记"未成交"。
- 已经"已转合同"的记录，点击能直接跳转到对应的合同和租户详情。

## 6. 各模块字段清单

### 6.1 房源字段

| 字段 | 说明 | 看房人侧详情页是否展示 |
|---|---|---|
| 封面图/图片 | 房源照片，支持多张 | 展示 |
| 小区/位置 | 房子在哪个小区/大概位置 | 展示 |
| 户型 | 几室几厅 | 展示 |
| 面积 | 平方数 | 展示 |
| 租金 | 每月多少钱 | 展示 |
| 押付方式 | 比如押一付三、押二付一 | 展示 |
| 朝向 | 朝南/朝北等 | 展示 |
| 楼层 | 第几层，共几层 | 展示 |
| 简介 | 文字描述，房子有什么特点 | 展示 |
| 联系方式说明 | 引导用户点"咨询"按钮的提示文字 | 展示 |
| 状态 | 可以租 / 已预定 / 已租出，由合同的建立/生效/结束自动决定 | 不展示（看房人只能看到"可以租"的房源） |
| 关联的咨询记录 | 这套房源历史上收到过哪些人的咨询，管理侧点进去可查 | 不展示，仅管理侧可见 |
| 关联的合同 | 当前（或历史上）绑定的合同 | 不展示，仅管理侧可见 |

### 6.2 咨询记录字段（新增）

| 字段 | 说明 |
|---|---|
| 看房人 | 对应哪个微信身份（openid），系统自动记录 |
| 关联房源 | 这条记录对应问的是哪一套房子，系统自动记录 |
| 首次咨询时间 | 点击"咨询"按钮的那一刻，系统自动记录 |
| 跟进备注 | 管理员手动追加的多条备注，按时间顺序排列（比如"觉得贵""下周三看房""决定不租了"） |
| 状态 | 跟进中 / 未成交 / 已转合同。签约时自动变"已转合同"；管理员判断没戏了可手动标"未成交" |
| 关联合同 | 如果这条记录后来转成了合同，这里能直接跳转过去 |

### 6.3 租户字段

| 字段 | 说明 |
|---|---|
| 姓名 | 租户的名字 |
| 联系方式 | 手机号或微信联系方式 |
| 当前状态 | 待入住 / 在租 / 曾租过 / 签约未入住，根据这个租户名下全部合同计算，不按最新一份合同简单判断 |
| 关联的咨询记录 | 这个人签约前对这套房源发起过的咨询和跟进记录，签约时自动关联，不需要重新填写 |
| 关联的合同 | 这个人名下所有的合同（可能不止一份，比如租过又续租、或换过一套），续租产生的合同能看出彼此的先后链条 |

### 6.4 合同字段

| 字段 | 说明 |
|---|---|
| 关联房源 | 这份合同对应哪一套房子 |
| 关联租户 | 这份合同对应哪一个人 |
| 起租日期 | 约定可以开始入住的日期；到了这一天系统会检查是否有未结束的生效中合同，没有冲突才把合同改为"生效中" |
| 到期日期 | 约定租期的最后一天；到了这一天不会自动结束合同，只会提醒管理员确认 |
| 实际结束日期 | 管理员结束合同时填写。正常到期通常等于到期日，提前退租填写真实退租日；系统用它判断后面的合同是否冲突 |
| 月租金 | 每月租金金额 |
| 押金/押付方式 | 比如押一付三 |
| 状态 | 待生效 / 生效中 / 已结束。起租日到了且没有未结束的生效中合同时，系统才把待生效改为生效中；到期日到了不会自动结束，已结束必须由管理员确认 |
| 终止原因 | 仅"已结束"状态需要填写：到期结束 / 提前退租 / 签约未入住取消，三选一 |
| 续租自 | 如果这份合同是续租产生的，这里记录它续租自哪一份旧合同 |
| 到期提醒 | 到期后显示"已到期，待确认结束"，提醒管理员处理；这不是合同状态 |

### 6.5 合同日期检查规则

- 起租日期和到期日期都算在本合同租期内。无缝续租时，新合同从旧合同到期日的次日开始。
- 新建或编辑合同，保存前都要检查同一房源的其他合同。日期重叠时禁止保存，并显示冲突合同及其日期，不能只提示"保存失败"。
- 未结束的合同按约定到期日检查；提前结束的合同按实际结束日期检查；"签约未入住取消"的合同不占用租期。
- 提前结束旧合同时，如果填写的实际结束日期与已经建立的后续合同重叠，不能直接完成结束操作，管理员需要先调整后续合同日期。
- 一套房源同一时间最多只能有一份"生效中"合同。待生效合同到了起租日，如果旧合同仍未结束，就继续保持"待生效"并显示"旧合同未结束，暂不能开始"。

### 6.6 房源和租户状态计算规则

#### 房源状态

- 只要有一份"生效中"合同，房源就是"已租出"。
- 没有"生效中"合同，但有一份或多份"待生效"合同，房源就是"已预定"。
- 既没有"生效中"，也没有"待生效"合同，房源才是"可以租"。
- 已取消和已结束的合同只保留历史，不再占用房源的当前状态。

#### 租户状态

按以下顺序检查这个租户名下的全部合同：

1. 有任意一份"生效中"合同 → "在租"。
2. 没有"生效中"，但有任意一份"待生效"合同 → "待入住"。
3. 没有进行中的合同，且历史上有"到期结束"或"提前退租" → "曾租过"。
4. 以上都没有，但有"签约未入住取消"记录 → "签约未入住"。

例如，一个租户以前住过一套房，后来又签了一份还没开始的合同，他现在显示"待入住"；如果他同时还有另一套房正在住，则显示"在租"。不能因为某一份新合同被取消，就覆盖掉他其他合同带来的状态。

## 7. 明确不做的事（避免AI画蛇添足）

- 不做看房人的注册/登录功能，看房人不需要账号就能看房源、发起咨询（身份识别是系统后台悄悄做的，用户无感）。
- 不做"填表预约看房"这种表单，咨询统一走微信客服会话，跟进备注由管理员事后手动补录。
- 不做多个房东/中介入驻发布房源的功能，房源只有管理员自己维护。
- 不做小程序内支付/签约功能，签合同收钱都在系统外面完成，系统里的"合同"只是记录条款和状态，不处理真实的资金往来和电子签名。
- 不做收款/账单管理、报修/维修管理，这两块留作以后扩展，这次不设计具体页面和字段。
- 不做地图定位、周边配套（地铁/学校）这类信息，第一版先不加。
- 不做管理员之间的权限区分，现阶段所有管理员账号能做的事都一样。
- 不做咨询记录的自动删除/合并功能，一人一房一条记录长期保留，方便回溯完整历史。

## 8. 待定事项（不影响这次UI设计，后续开发前再定）

- 小程序注册主体：个人还是公司主体，会影响能否顺利通过微信审核，但不影响页面长什么样。
- 具体用什么技术框架开发（原生小程序 / 跨端框架），属于工程实现问题，不影响UI设计。
- 管理员登录具体用什么方式验证身份（账号密码、手机验证码等），属于工程实现细节，不影响UI设计（本文档默认页面上有一个正常的登录入口即可）。
- 系统多久检查一次"待生效"合同是否可以开始，属于工程实现细节；但产品规则已经确定：到了起租日且没有未结束的生效中合同，才可以变成"生效中"，到期日不会自动结束合同。

## 9. 给AI设计UI图的补充说明

- 整体风格：偏生活化、亲和，不要做得像正式的房产中介平台那么"商业感"，因为主要靠小区内部推广，用户对象是普通住户。
- 看房人侧两个页面（列表页、详情页）请重点设计，样式偏轻松；管理侧的五个页面（房源管理、房源表单、咨询/跟进列表、租户管理、合同管理）功能优先，样式简洁清晰即可。
- 请特别体现第5节里提到的几个核心体验点：
  - 看房人侧的"信息分层"（哪些信息第一眼看到、哪些往下翻才看到）。
  - 管理侧房源列表（可以租/已预定/已租出）和合同列表（待生效/生效中/已结束）里的"状态标签"，要有明显的视觉区分，最好用三种不同颜色区分，不要只用两种颜色简化处理；到期但未确认结束的合同要额外显示"已到期，待确认结束"提醒，不能把它画成第四种合同状态。
  - 咨询/跟进列表页要突出"筛选"能力（按状态筛出"跟进中"的记录），这是这次新加的、专门用来防止潜在租户被遗忘的页面，设计时可以给它一个醒目一点的入口位置。
  - 房源、咨询/跟进、租户、合同这四个管理页面之间要能互相跳转（比如从一条已租出的房源点进去，能直接看到对应的合同和租户；从租户详情能看到签约前的咨询记录），体现这是一套互相关联的系统，不是四个孤立的列表。
  - 新建合同、续租和结束合同的页面要能展示日期冲突提示；提示中要说清楚冲突的是哪套房、哪份合同、哪两个日期，不能只显示笼统的报错。
